# 문구와 속도 규칙

화면에 나가는 모든 글자(헤드라인, 설명, 이름)와 설명이 머무는 시간에 대한 규칙이다. 원칙 번호는 principles.md를 가리킨다.

## 헤드라인

- 제품 런칭 영상 카피처럼 짧고 단정하게 쓴다. 대구와 대비(잠든 → 일하는), 명사로 끝내기, 한 줄에 한 메시지.
- 설명조("~를 처리", "~로 등록")와 개발 메모 같은 표현은 쓰지 않는다.
- 12자 안팎으로 쓴다. 썸네일 가운데 880px에 들어가야 한다(굵은 60px 기준 한글 한 자가 약 60px).
- 뜻이 흐린 낱말(느긋이, 결)과 명사 나열(공정·품질·생산)을 피한다.
- 숫자는 원문 사실이면 써도 되지만 숫자 없는 카피를 먼저 찾는다. 예: "12개 소스의 하루" 대신 "공개 소스의 하루".
- 영어 기술 용어는 꼭 필요할 때만, 정확한 표기로 쓴다.
- 과장은 되지만 자료의 범위 제한과 부딪치는 말은 안 된다(P13).

## 설명을 넣을지 판단

1. 장면마다 묻는다: 그림만 보고도 무슨 일인지 아는가? 알면 넣지 않는다. 처음 보는 사람이 "이게 뭐지?" 할 장면이면 넣는다.
2. 영상마다 설명 모양을 하나 고른다(styles.md). 이름 있는 단계나 모듈이 차례로 나오면 "이름 + 두 줄" 모양, 한 흐름으로 이어지는 장면이면 "두 줄만" 모양이 맞기 쉽다.
3. 한 영상 안에서는 한 모양으로 통일한다. 섞는 편이 분명히 더 잘 이해될 때만 섞고 이유를 기획서에 적는다.
4. 기획서에 장면별 판단 표를 둔다: 장면, 필요 여부, 이유, 이름, 두 줄, 자료 근거.

## 설명 문장

형식
- 두 줄. 줄마다 명사로 끝나고 마침표는 찍지 않는다.
- 첫 줄은 화면에서 일어나는 일, 둘째 줄은 보는 사람이 얻는 이득.
- 한 줄 22자 이하(공백 포함). 이름은 짧은 말로, 개발 용어(빌드, 린터 등) 없이.
- 친구에게 화면을 보여 주며 말하듯, 소리 내어 읽었을 때 자연스러워야 한다.

좋은 예
- 사진을 올리면 바로 붙는 이름표 / 하나하나 적지 않아도 되는 정리
- 밤새 쌓인 기록을 모은 한 장 / 아침에 한눈에 보는 어제
- 문제가 있는 줄만 켜지는 화면 / 고칠 곳부터 보이는 목록

하지 말 것
| 종류 | 나쁜 예 | 고친 예 |
|---|---|---|
| 대응표처럼 늘어놓기 ("A는 B, C는 D") | 빨강은 오류, 초록은 통과다 | 문제가 있는 줄만 켜지는 화면 / 고칠 곳부터 보이는 목록 |
| 명사 나열, 쉼표 압축 | 수집·정제·색인 | 매일 새로 모아 오는 자료 / 찾기 좋게 다듬어진 목록 |
| 번역투, 딱딱한 전문어 ("수행한다", "~에 대해", "판정한다") | 입력에 대해 유효성 판정을 수행 | 잘못 들어온 값을 걸러 내는 검사 / 믿고 쓰는 결과 |
| 구현 명세 읽어 주기 (방법만 있고 무엇이 되는지, 왜 좋은지가 없음) | 문서를 잘라 벡터로 바꾸고 상위 다섯 개를 고름 | 질문과 가장 가까운 문단을 찾는 검색 / 출처까지 함께 보이는 답 |
| 추상 명사(단서, 구성, 표식, 흐름), "~하는 ~" 꾸밈 겹치기 | 신호를 살피는 구성 / 흐름을 읽는 처리 | 화면에 보이는 것과 사람이 얻는 것을 구체적으로 |
| "~다", "~요"로 끝내기, 마침표 | 검사기가 칸을 찾아 경고한다. | 혼자 튀어나온 칸을 찾아 주는 검사기 / 고치는 건 사람의 몫 |

그 밖의 규칙
- 숫자를 넣지 않는다. 헤드라인에 나온 숫자를 풀어 설명하지도 않는다.
- 이득은 자료에 있는 것만 쓴다. 그럴듯한 장점을 지어내지 않는다. 자료에 없는 동작(예: 알림만 있는데 "물어보는")도 쓰지 않는다.
- 이름을 설명에서 되풀이하지 않는다. 같은 시간에 떠 있는 헤드라인의 말을 되풀이하지 않는다(P42).
- 아직 화면에 안 나온 것을 설명하지 않는다. 설명은 그 내용이 화면에 나오고 0.5초 이상 지난 뒤 뜬다.
- 점검 질문: 이 문장을 들은 사람이 "그래서 뭐가 좋은데?"라고 되묻게 되면 고친다.
- 다 쓴 뒤 한 번 더 소리 내어 읽듯 다듬고, 고치기 전과 후를 기록에 남긴다.

자동 점검(설명 문장만 한 줄씩 담은 파일 lines.txt에 대해)
```bash
grep -nE '\.$|[0-9]|(다|요)$' lines.txt                          # 마침표, 숫자, 다/요 끝 (긴 줄표 U+2014도 눈으로 확인)
LC_ALL=C.UTF-8 awk '{ if (length($0) > 22) print NR": "length($0)"자 "$0 }' lines.txt   # 22자 초과(글자 수로 센다)
```
`LC_ALL=C.UTF-8`을 빼면 Git Bash의 awk는 바이트를 세어 한글 한 자를 3으로 센다. macOS에 `C.UTF-8`이 없으면 `en_US.UTF-8`을 쓴다.

## 속도와 머무는 시간

- 머무는 시간은 설명 글자 수(이름과 두 줄, 공백 포함)를 11로 나눈 초이고, 최소 2초다. 타자처럼 찍히는 연출 시간도 여기에 포함한다.
- 등장과 퇴장 연출(타자, 선 긋기, 창 열기)은 0.5초 안에 끝낸다. 예: 창 열기 0.15초, 닫기 0.12초, 글자 전체 0.5초 안에 찍힘.
- 설명이 떠 있어도 장면은 멈추지 않는다. 멈춤(hold) 대신 속도 곡선으로 그 구간만 늦춘다(0.3~0.9배). 나머지 구간은 1.0~1.35배로 당길 수 있다. 곡선의 마디 사이는 코사인으로 부드럽게 잇는다(템플릿의 KN).
- 카메라가 고정된 구간을 늦출 때는 서 있지 않게 아주 조금 밀어 들어간다.
- 설명은 그림과 겹치지 않는다. 필요하면 장면을 비켜 세우거나 줄이고, 화면 가장자리에서 잘리지 않게 한다.
- 설명은 장면에 붙어 카메라와 함께 움직이거나, 큰 카메라 이동이 시작되기 전에 빠진다.
- 다음 설명은 앞 설명이 완전히 빠진 뒤에 들어온다.
- 길이 목표는 50~75초다. 약 50초짜리가 "좋다"는 평가를 받은 속도감의 기준이었다. 내용이 많으면 넘어도 되지만 늘어지면 안 된다.
- 같은 구도로 6초 넘게 서 있지 않는다(P28).
- 길이가 바뀌면 음악과 효과음 큐도 같은 곡선으로 옮긴다(P61).
